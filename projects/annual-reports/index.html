Financial-statement extraction service for A-share company reports

Pulling the balance sheet, income statement and cash-flow statement out of every A-share annual report for 2025, and saying how far each number can be trusted.

When
September–October 2026
Role
Led the project; built the extraction layer, the dataset and the evaluation
Code
Not public

The first finding

Before writing any extraction code I looked at the comparison everyone was using to judge the parser. It reported 17,405 differences in the cash-flow statements against a commercial financial database, most of them marked “missing in the reference”.

Almost none of that was the parser. In 97.9% of the “missing” cases the stock code had changed: 230 companies on the Beijing Stock Exchange moved from 83/87 codes to 920 codes in 2025, and the reference only keeps data under the current code. Another large group came from comparing restated prior-year figures with the originally published ones. With the comparison fixed, problems on the parsing side made up 4.8% of the cash-flow differences.

That set the rule for the rest of the project: every number gets a script that reproduces it, and a disagreement is not an error until we know which side is wrong.

How it works

  1. Find the pages. Only the pages that hold the three statements are sent to the document parser (MinerU), which keeps the GPU cost low and the output small.
  2. Rebuild the tables in plain code. Continued tables are joined, the current and prior-period columns are identified, and units are read from the page.
  3. Map rows to about 270 standard fields. The mapping is learned, not written by hand: 11,520 row-name aliases and 35 field formulas, found by matching numbers against reference data on a development set. There is no rule for any particular company or line item.
  4. Check the result. A report is accepted only if units are consistent, ten key fields come from the statement itself, and the accounting identities hold. Otherwise it goes to a human review queue with the reason attached.
  5. Attach a confidence to every value: how often the alias or formula that produced it was right on the development set, as matches / (uses + 1).

Results

The headline numbers come from 1,200 reports the mappings had never seen, drawn as two frozen samples and evaluated once each. 99.3% passed the checks, and 99.8% of those had all ten key fields right. Across every field, precision was 99.85% at 98.06% coverage. These are non-financial companies; banks and brokers are harder (see below).

The same mappings, without relearning, were then run on 382 annual reports from the previous year. All 290 non-financial reports passed, and on the same companies each statement’s coverage stayed within 0.3 percentage points of the newer year. The full set of 5,488 companies runs in 93 seconds once parsed, 5,451 of them pass, and two runs with different hash seeds produce byte-identical output.

The confidence score is useful in practice. Keeping only values above a threshold trades coverage for precision in a predictable way:

Keep values with confidence ≥PrecisionCoverage
0.5 (everything)99.85%98.06%
0.9599.89%96.76%

All of these are agreement with a commercial database whose own labels contain mistakes. Disagreements were attributed automatically to the extraction or to the label, and there was no random human audit, so read them as strong agreement rather than measured truth.

What did not work

I tried letting language models map the rows the aliases could not. When two inexpensive models agreed on a field, they were right only 82% of the time, well below what the learned mappings achieve. They now only propose candidates, and a candidate is used only if the numbers confirm it.

Financial companies are the weak spot. Their statements use their own line items, about 86% of them pass the checks, and cash-flow coverage for them is around 87%. Those reports are the main item on the review list.
