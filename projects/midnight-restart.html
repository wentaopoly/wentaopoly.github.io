The cause turned out to be two deadlocks stacked on top of each other. meta: When: January–August 2026 Role: Design and implementation Code: Not public ---

The setup

A Python process drives a logged-in Chrome through browser-use, reads articles section by section, and hands each one to a Kafka topic. An article is marked done only after the broker acknowledges it, and per-section progress is written atomically, so a crash at any point does not lose an article. Once a day, at midnight, the worker closes the browser and replaces itself with a fresh copy through os.execv.

The symptom

At the midnight restart the worker simply stopped. The process was still there and every PID-based health check passed, but no article arrived. The one visible clue was in the process list: a healthy session has nine Chrome processes for its profile, and a stuck one had a single process left. It was not intermittent; both nights we examined, it hung in exactly the same place.

Layer one

The library’s stop() tears Chrome down first, then waits for a completion signal on its event bus. That signal can never arrive, because the handler that would send it needs the DevTools connection stop() has just closed. The event bus also swallows CancelledError while cleaning up.

So the obvious timeout does not time out. asyncio.wait_for cancels the task when time is up and then waits for the cancellation to finish, which never happens here.

# hangs: wait_for needs the task to accept cancellation
await asyncio.wait_for(browser.stop(), timeout=12)

# returns after 12 s whatever the task does
task = asyncio.ensure_future(browser.stop())
await asyncio.wait({task}, timeout=12)
# then abandon the task and kill Chrome by its profile path

Layer two

Fixing the first layer only moved the hang. On the way out, asyncio.run cancels every pending task and waits for each of them, including the abandoned stop() that will never finish. The process never reaches os.execv.

The fix is to run the main coroutine with loop.run_until_complete, which leaves pending tasks alone. When os.execv replaces the process image, the stuck task disappears with it.

Both layers have regression tests that use a stop() which really swallows cancellation. If either fix is undone, the test hangs instead of passing quietly.

Smaller lessons

  • “Alive” is not a useful health signal for a worker. The alert that matters is “the broker has acknowledged nothing for 60 minutes”, and its state is stored on disk so a restart does not fire it twice.
  • That watchdog is the last thing cancelled on shutdown. If it goes first, a stuck shutdown is also a silent one.
  • A deadlock that happens at the same time every night is a gift. It is far easier to catch than one that happens once a month.
