Agent Claim Network

Agent Claim Network is a terminal coding agent that saves what it figures out as “claims” other agents can look up. I ran the evaluation that asks whether those claims actually help, on 111 long software-engineering tasks.

When
2026
Role
Evaluation, and several agent features, in a team project
Code
agent-claim-network · acn-deepswe-eval

The idea

Most multi-agent setups share a memory store and leave it there. ACN instead stores conclusions as claims: a statement with a scope, its evidence, who holds it and how confident they are. A router indexes claims so other agents can find them, and a maintainer handles the cases where two claims disagree. The core design is the team’s; my question was narrower.

If one agent solves a task and leaves claims behind, does a fresh agent on the same task do better?

Setup

The benchmark is DeepSWE v1.1, long tasks written from active open-source repositories and checked by hand-written verifiers. Each task was given to four isolated agents running DeepSeek-V4.1-Flash, identical except for how claims reach them:

  • Producer solves the task first and writes claims. Only producers that pass the verifier get to hand their claims on.
  • No claims: a fresh agent, the baseline.
  • Claims on demand: a fresh agent that sees a list of claim summaries and fetches the ones it wants.
  • Claims forced: a fresh agent with every claim pasted into its first prompt.

Results

The agent that fetched claims on demand passed 10 more tasks than the baseline and used 15.9% fewer input tokens and 10.3% fewer model requests. Pasting the same claims into the prompt gained only 2 tasks, so the benefit comes from the agent choosing what to read, not from more context.

That is encouraging, but not conclusive. Paired by task, the two arms disagree on 30 tasks:

Baseline passed5310

Twenty to ten points the right way, but an exact McNemar test gives p ≈ 0.099, and this is a single run. In an earlier full run with the previous model, DeepSeek-V4-Flash, the claim arm did worse than the baseline (44 against 52 of 113). I would want repeated runs before calling this an effect.

What I built

  • The DeepSWE runner and the evaluation itself: four isolated arms per task, the quality gate on claims, paired statistics, and a report that only counts runs that finished with a full denominator.
  • The claim tool agents use to look claims up in the middle of a task, and the /claim panel in the terminal UI.
  • OAuth login for MCP servers, and recovery when a model provider rejects a request mid-session.
